# Decisions (settled; ask before changing)

| Date | Decision | Why |
|------|----------|-----|
| 2026-10-02 | TypeScript + Vite, no frameworks | Types catch AI mistakes; zero runtime cost |
| 2026-10-02 | Biome for lint/format, Vitest for tests, all behind `npm run check` | One command tells the AI whether it broke something |
| 2026-10-02 | ASCII art is bundled via `import.meta.glob` from `src/ascii-art/` (no fetching); every HTML page is listed in `vite.config.js` | Runtime fetching looped forever in dev (Vite answers missing files with index.html) |
| 2026-10-02 | Card text goes through `toHtml()` which escapes everything; links are placed by position | Old string-replace broke on `<`, `&` and duplicate words |
| 2026-10-02 | Features are folders `src/features/<name>/` exporting one object (`id`, `card()`, optional `page`); features never import each other, shared code in `src/core/` | Keeps each AI session inside one folder (see ARCHITECTURE.md) |
| 2026-10-02 | Oracle is a broadcast, not a chat: one self-hosted small model streams its "thoughts" to all visitors via SSE; no visitor input, no paid APIs | Cost and abuse do not grow with visitors; coherence matters more than the smallest footprint |
| 2026-10-02 | Hosting: own netcup server, domain 1000110.xyz. Traefik is the only reverse proxy; site is an `nginx:alpine` container (stack `/opt/stacks/1000110-xyz`) serving a bind-mounted `dist/`. CI rsyncs `dist/` as an unprivileged `deploy` user restricted by rrsync to that directory (`deploy/setup-server.sh`) | No second proxy; deploy is a file sync; a leaked CI key cannot reach Docker |
| 2026-10-02 | `.gitattributes` forces LF line endings everywhere | Windows CRLF checkouts made `npm run check` fail locally while CI passed |
| 2026-10-02 | Font is DejaVu Sans Mono (self-hosted woff2 in `public/fonts/`, full glyph set; replaces Space Mono from Google Fonts). It has box drawing, block elements and geometric shapes but NO braille or legacy computing symbols; GNU Unifont (subset, 12 KB) was tried and rejected: the bitmap look is bad in a browser. JGS (`jgs7`, 14px) was tried and rejected: perfect for the ASCII art but hard to read as text; it covers every glyph we use, so it stays in `public/fonts/` for art-only use. No font toggle. One font for the whole grid, because a fallback font has other glyph widths and breaks alignment | Space Mono lacked box drawing, so `single/double/rounded` borders were misaligned; self-hosting also removes the Google request |
| 2026-10-02 | `<noscript>` cards are generated at build/dev time from `src/cards.ts` by `plugins/noscript-cards.js`, never written by hand; the border is hardcoded once in `buildHomeCards` | One source for both versions; the hand-written copy had to be edited for every card change |
| 2026-10-02 | The binary footers stay hidden easter eggs: no decode animation, no hints, no hover/click reveal | The charm is that visitors find and decode them themselves |
| 2026-10-02 | Cards use the `rounded` border, hardcoded in `src/index.ts`. Styles (none, retro, ascii, single, double, rounded) stay as data in `src/borders.ts`; `<noscript>` cards carry the same rounded frame. The toggle (key `b`, localStorage setting) was built, tried and removed | The user wants one fixed look for now; re-adding a toggle is easy because styles are data |
| 2026-10-02 | Blog frontmatter is parsed by a small hand-written parser (`key: value` and inline `[a, b]` only, throws with the filename on bad input); posts are bundled at build time via `import.meta.glob` from `src/features/blog/posts/` | Zero runtime dependencies; `gray-matter` needs Node `fs`/`Buffer` and is unmaintained; richer YAML can be swapped in later behind `parsePost` |
| 2026-10-09 | Card footers (hidden binary messages) use `card.drawFooter(text)`: fixed 4 lines at the bottom, padded with spaces to 16 characters, throws if too long or overlapping content | Footers were placed with hand-counted `emptyLine`s and drifted (the blog card had 3 lines, not at the bottom) |
| 2026-10-09 | Cards are for the home grid and widgets only. Blog posts are read on a full page styled as a pager (72ch column, native scroll, fixed status line with the progress meter, hash routing `/blog/#slug`), rendered by a small hand-written Markdown-to-HTML converter | Reading long text in a 41x32 card is painful; a normal page keeps selection, find, links and phone scrolling while the look stays terminal-like |
| 2026-10-09 | Card colors are a per-cell style layer in the card engine (`CardStyle` names, `<span class="c-NAME">` in `toHtml()`), colored by theme variables in `card.css`; titles yellow, borders and footers gray, art accents per card. Home keys: h/j/k/l always, arrows only once a card is focused, so plain scrolling keeps working | One engine feature colors the JS cards and the generated `<noscript>` cards alike; hijacking arrows from the start would break keyboard scrolling on the one-column mobile layout |
| 2026-10-10 | Design system (DESIGN.md): one shell (crumbs, man header, `$` prompt lines, end prompt with cursor, bottom status line) for every page, phone first (40 columns, fluid font under ~400px, 44px tap targets, safe area, short window names). Card titles are commands (`$ cat about`) with a dim `$`; cards are widgets inside the shell | The home page and the blog felt like two different sites; one shared vocabulary lets each page keep its own content |
| 2026-10-10 | Home card grid columns are exactly `41ch` wide and the home wrapper is sized from the column count, not `fit-content` | `fit-content` followed the longest header line, so the header was wider than the cards on phones |
| 2026-10-10 | Every page is built by one frame, `renderPage` (crumbs, man header, `$ command`, body, optional secret, end prompt), and listed once in `src/core/site.ts`; the status line (site windows left, clock and progress right) and the keys (1-9, j/k, g/G, b/Esc) are shared too. Tests (`assertShell`, site map vs `vite.config.js`, built pages) fail when a page skips a part | Home, blog index and post each assembled the shell by hand and drifted (missing header and end prompt, different status lines); a page can now only supply its body |
| 2026-10-10 | The home page is a session (one command per section), not a grid of cards. The card engine, its colors and tests stay as a toolkit for later widgets; the home cards, blog card, card keyboard navigation and card windows were deleted (git history keeps them) | The 41 x 32 tile forced a fixed width, equal weight and centered text, so home felt unlike the blog |
| 2026-10-10 | Hidden messages are a shared `secretBlock` (dim binary, 4 bytes per line, aria-hidden), in the frame's `secret` slot or per section; blog posts may set `secret:` (max 32 characters). No hints, no decode | Keeps the easter eggs from the cards on every page and lets each post hide its own |
| 2026-10-10 | The home page imports all blog posts into its bundle (it lists the newest five with word counts) | Simple for a few posts; replace with a generated post index (the RSS task makes one) when the blog grows |
| 2026-10-10 | The blog admin is hand-written, not an existing CMS (Decap, Keystatic, Tina), and is one module of a shared admin (infrastructure first, then a module per feature). Storage: the admin commits posts to the repo (option A) so git stays the single source of truth and CI validates and deploys; posts are not moved to server files | The needs are narrow (flat Markdown files, the shell look, Pocket ID auth, phones); CMSs bring their own UI, GitHub-only login, React and config; the hard parts (auth, repo commits) are not removed by a CMS |
| 2026-10-10 | The RSS feed (`/feed.xml`, RSS 2.0, full post content) is generated at build time by `plugins/rss-feed.js` from `getPosts()` and `renderMarkdown`, and served by a middleware in dev; never hand-written. Item links and guids are the reader's hash URLs (`/blog/#slug`); `lastBuildDate` is the newest post date, not the clock, so builds are reproducible. Discovery is a `<link rel="alternate">` in the head only, no visible link | One source for the blog and the feed; real `/blog/<slug>/` pages are a separate task, and a visible link would be its own design-system decision |
| 2026-10-10 | Tools live on one page, `/tools/`, with hash routing (`/tools/#<id>`); each tool is a folder `tools/<id>/` with an eager `meta.ts` and a lazy `index.ts` (own chunk), found by `import.meta.glob`; `mount` may be async and return a `cleanup`. Public tools run in the browser and are listed; tools that need the backend are `access: "private"` (owner only behind Pocket ID, never listed publicly, not built before Phase 6a). Status line order is home, blog, tools, exp | A new tool must not touch `site.ts` or `vite.config.js`; heavy dependencies stay in one tool's chunk or on the backend; the public site can say nothing is uploaded |
| 2026-10-17 | Tools are implemented in batches of 3 to 4 grouped by shape (A generators and crypto, B text and data, C calculators), but shipped and listed as separate tools: each keeps its own folder, registry entry, route and chunk. One branch and PR per batch, one commit and tests per tool; "one task" means one batch | The registry made a tool cheap, so the per-session overhead (branch, plan, check, docs) outweighed the tool itself |
| 2026-10-18 | Color themes are `[data-theme="<id>"]` blocks of the nine variables in `theme.css` (six: gruvbox dark and light, amber crt, green phosphor, solarized dark, nord); raw hex stays in that file only. The choice is `localStorage["theme"]`, absent = `auto`, which follows the system (gruvbox light or dark). `/theme/` is the fifth status line window (`5:theme`) and the `t` key cycles; a `◐` link was tried and dropped. Five windows leave no room for the percentage under 420px, so it hides there. A blocking inline script, injected into every head by `plugins/theme-boot.js`, sets `<html data-theme>` before first paint. Tests enforce contrast floors per theme | One variable layer already exists, so a theme costs no component changes; the inline script is the only way to avoid a flash of the default theme with deferred module scripts; following the OS by default respects visitors who never open the picker |
| 2026-10-17 | Syntax highlighting uses `highlight.js` (core plus only javascript/typescript, css, xml/html, markdown, bash), loaded in a lazy chunk; json, diff and regex highlighting stay hand-written and small. Colors come from theme variables via a CSS block that maps the classes | Generic tokenizers are a solved problem; json, diff and regex are tiny or already tokenized by our own code and a generic highlighter does not know them. The one runtime dependency is approved by the user and must stay out of pages that do not highlight |
| 2026-10-18 | The highlighter lives in `src/core/highlight/` (not in the tools folder) because the blog and the tools both use it and features never import each other. `highlight.js` is imported only in `generic.ts`, reached by a dynamic `import()`, and a build test checks no page entry or preload names it. Editable fields use an overlay (colored `<pre>` behind a transparent `<textarea>`, same metrics, scrollbar width copied); read-only output is a colored `<pre>` while copy and "send to" use the raw text. Past 200,000 characters json is shown uncolored. The blog renderer stays synchronous and pure (the RSS feed uses it): code boxes carry `data-lang` and the page swaps in colored boxes after render. The regex pattern field has no overlay (a single-line input scrolls sideways); its explain tokens are colored. Encode (html) output is not highlighted (user decision) | One shared module, no cost for pages that never highlight, and the character grid in code boxes never shifts |
| 2026-10-17 | Tool state lives in the hash query (`#json?i=...&m=format`); `parseRoute` reads only the id. Options are remembered in localStorage (per tool and key) but typed text never is: it only travels in a link the user copies with "copy link" (values over 4000 characters are left out, secrets such as the HMAC key are never included). Received link values do not overwrite the user's remembered options | Typing must not spam history or leave text in storage; a link has to reproduce the result, so defaults are written into it too |
| 2026-10-17 | "Send to another tool": a tool with one main text box sets `pipe: true` in its `meta`; the sender parks text in sessionStorage (`tools:pipe`) and changes the hash; the target's primary `bindText` takes it once | No shared global state, works with the lazy chunks, nothing is left behind |
| 2026-10-30 | The `sc2bp` tool (SoundCloud playlist to Beatport playlist) is the first tool that talks to the server, and it is listed publicly. Judgement stays in the browser (`parse.ts`, `match.ts`, `review.ts`, tested by `npm run check`); a small Python service in `sc2bp/` only lists the playlist (`yt-dlp`), searches Beatport and creates the playlist, behind the shared `tinyauth` forwardauth middleware on `/api/sc2bp`. The page is static and public (a hash route cannot be gated by Traefik); on load it calls `/api/sc2bp/me` and goes to the tinyauth login (address from the `X-Tinyauth-Location` header, return address pointed back at the tool; a session flag stops a login loop). No per-user check: tinyauth is owner-only. The tool never claims "nothing is uploaded". Beatport has no public API, so the service uses the unofficial route (public `client_id` from the v4 docs page, the owner's own login), a ToS grey area accepted for personal use | Tune My Music costs money; a wrong silent match is the worst failure, so scoring is strict and unit tested, while the unofficial, breakable parts (Beatport, `yt-dlp`) sit in one small replaceable service |
| 2026-10-30 | sc2bp runs as background jobs on the server and supersedes the row above (matching in the browser). A conversion must go on with the page closed, so the whole pipeline (list, read, match, create) runs in the `sc2bp/` service: one worker, one job at a time, each job a JSON file in `/data/jobs/` written after every batch so a restart resumes it. The matching logic is ported to Python (`parse.py`, `match.py`) and is the only implementation; the TypeScript copy is deleted, and `tests/fixtures/real_expected.json` (30 real tracks, produced by the TypeScript version) pins the port. The job creates the Beatport playlist by itself from confident matches; `maybe` and `none` tracks wait for an optional review that can add them later. Up to 1000 tracks. pytest for `sc2bp/` runs in CI | Jobs can take many minutes and must survive a closed tab or a restart; two implementations of the scoring would drift; the user does not care about speed but wants a progress view, real error handling and no track-by-track screen by default |
| 2026-10-31 | Uptime Kuma (`kuma/compose.yaml`, pinned `louislam/uptime-kuma:2.5.9`, stack at `/opt/stacks/uptime-kuma/`) does monitoring and email alerts; the site's own `/status/` page reads its status-page JSON. Two Traefik routers: the admin UI on `kuma.1000110.xyz` behind `tinyauth`, and `1000110.xyz` + `PathPrefix(/api/status-page)` + `Method(GET)` with no auth (priority 100, nothing else of Kuma is public) | We do not rebuild scheduling, history or alerting. The JSON is not a stable API, so the image is pinned and `parse.ts` validates (an unknown shape, or the HTML Kuma returns before a status page exists, is "status unavailable"). Not `read_only`: Kuma writes SQLite and temp files |
| 2026-11-01 | The Kuma status view is a tool (`/tools/#status`), not a `/status/` page, and it is owner only: the `kuma-status` Traefik router gets the `tinyauth` middleware (reverses "no auth" in the 2026-10-31 row) | The owner does not want another status line window, and the information is only relevant to the owner. Following sc2bp: the tool page is static and listed, only the API is protected, and the tool sends you to login when the API says 401. Monitor names can now be descriptive. Shared login code moved to `src/features/tools/auth.ts` |
| 2026-11-01 | Stack deploys: the CI key (user `stackdeploy`, no docker or sudo group, `restrict,command=` forced to `stack-deploy-ssh`) can only send `[plan] <stack> <sha>`; a root script (`stacks/stack_deploy.py`, one sudoers rule) checks the stack against a root-owned allowlist, fetches the commit itself with a read-only GitHub deploy key and refuses one that is not an ancestor of `origin/main`, re-runs `stacks/lint.py`, validates with `docker compose config`, copies only tracked files (never `.env` or data, deletes nothing, keeps replaced files in `.stack-deploy-prev/`), runs `up -d --build --remove-orphans` and waits for healthy | CI never uploads files, so a leaked key cannot deploy a branch, a pull request or arbitrary compose. Root rather than the docker group: files in `/opt/stacks` belong to different owners, and the docker group is root anyway, so this keeps one small audited script as the only path. A new stack needs a line in `/etc/stack-deploy/stacks` on the server, which only the owner can add. Whoever can merge to `main` can still run containers as root: branch protection and 2FA guard that |
| 2026-11-01 | Deploy failures are watched by a Kuma `json-query` monitor `deploys` (group `ci`) on the public GitHub API `actions/runs?branch=main&status=completed&per_page=5`, expecting the newest non-cancelled run's `conclusion` to be `success` (JSONata), every 300 s | No credential, no CI change and no new public route (a push monitor would need a token held by CI and a public `/api/push/` route to Kuma, and would go down by itself after a quiet period). Covers every failed run on `main`: stack deploys, the site deploy and the tests. Limits: GitHub allows 60 anonymous requests an hour per IP and this uses 12; a green deploy of an unhealthy stack is caught by the per-service monitors, not by this one |
| 2026-11-01 | CI deploys stacks from `main` only: job `stacks-changed` (tested `stacks/changed.py`) picks `auto` stacks whose copied files changed, `deploy-stacks` runs them one at a time through the Environment `production` (or `production-approval`, which waits for the owner, for `approval` stacks); the key is an Environment secret, so it only reaches jobs on `main`; pull requests never deploy. Branch protection on `main`: pull request and the `check`, `sc2bp`, `stacks` jobs required, no force pushes, admin not enforced (the owner owns the repo) | The repo is public, so secrets must never reach pull request jobs. Re-running an old run redeploys that commit (usable as a rollback; the server only requires it to be on main). One-off or failed deploys: run the CI workflow by hand with the `stack` input |
